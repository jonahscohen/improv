Stage 3c of the sidecoach upgrade plan (`docs/superpowers/plans/2026-07-23-sidecoach-upgrades.md`). Goal: make the generated `product-rule-registry` the SINGLE manifest (rule id -> detector/severity/lens/surface-support) that the detect CLI + the audit + the eval scan resolve rules through, so adding a rule updates every surface. No new rule engine; behaviour-preserving. Authored against HEAD 1ea7ae73. NOT committed.

**The two orphans this surfaced (verify-check #2 is exactly about these):**
The rendered audit path fires the rule names the two rendered SCANNERS emit: objective `broken-image, skipped-heading, low-contrast, gray-on-color, justified-text`; subjective `tiny-text, nested-cards, marketing-buzzword, default-typeface`. Cross-checking against the registry found:
- `nested-cards` - fired by the subjective scanner, surfaced by audit-rendered, but had NO registry entry at all (true orphan). Not consumed by run-validator today.
- `low-contrast` - the scanner emits `low-contrast` but the registry rule is `a11y.color-contrast` (aliases `polish-standard:20`/`POLISH_020`), with no `rendered-scanner:low-contrast` alias, so the scanner name was not resolvable (alias orphan).

**What was built (files - all within ownership + the test):**
- `src/product-rule-registry.ts` - added `RENDERED_RULE_MANIFEST` (9 entries: 8 validator-owned bindings + nested-cards audit-only), `resolveRenderedRule(scannerRule) -> {lens, ruleId|null, canonicalRuleKey, severity, blocking, findingClass, registryScope, source}`, `renderedScannerRules()`, `listRenderedManifest()`. Added the `rendered-scanner:low-contrast` alias to `a11y.color-contrast` (consistency with the 7 other rendered decision rules). For validator-owned entries severity/findingClass are READ from the RAW_RULE via `getRuleById` (never duplicated) so the manifest can't drift from the rule it points at.
- `src/audit-rendered.ts` - additively routed the objective + subjective finding severity through `resolveRenderedRule` (the findings-mapping loop only; NOT the Ground B / committed-family region). The prior inline map (`objective error->blocking`, subjective `->warning`) is kept as a fail-safe fallback for an unregistered rule, so nothing can be silently dropped/downgraded.
- `bin/sidecoach-detect.js` - added `--list-rules` (enumerates the 60 validator-owned rules grouped by owner + the 9 rendered-scanner bindings; query mode, stdout, exit 0, no scan). Added `RULES`/`listRenderedManifest` to the dist require.
- `src/__tests__/product-rule-registry.test.ts` - the no-orphan test: imports the scanners' `OBJECTIVE_RULES`/`SUBJECTIVE_RULES` and asserts (a) every scanner rule resolves via `resolveRenderedRule` on the right lens [no orphan], (b) every manifest entry names a real scanner rule + exact count parity [no phantom], (c) a BEHAVIOUR LOCK pinning each rule's blocking|warning to the pre-consolidation mapping, (d) nested-cards is audit-only with `getRuleById('polish.nested-cards')===null`, (e) alias/manifest consistency. Updated the strict `a11y.color-contrast` expected row for the new alias.

**KEY DESIGN DECISION - why nested-cards is AUDIT-ONLY, not a RAW_RULE.**
Why: registering nested-cards as a rendered-scan RAW_RULE would trip the INVERSE INVARIANT in `validator-generation.ts` (every rule declaring `rendered-scan` evidence MUST be in `RENDERED_BACKED_RULE_IDS`), which promotes it to required-when-renderUrl-present. run-validator would then NEWLY consume nested-cards findings in the static-check lens (and the lane pipeline) - a behaviour change, violating "behaviour-preserving". How: registered it as an AUDIT-ONLY manifest entry (a separate list in the registry, `ruleId:null`), resolvable for lookup/enumeration but NOT a validator-owned decision rule. This keeps the registry the single manifest for every fireable rendered rule WITHOUT touching the decision path. `RULES.length` stays 60; `validators.generated.ts` is byte-identical (empty diff - proven), confirming the derivation is untouched.

**Behaviour-preservation, proven not asserted.** The registry canonical severity mapped to blocking|warning EXACTLY reproduces audit-rendered's old hardcoded mapping for all 9 rules (broken-image/skipped-heading/low-contrast/gray-on-color = blocker/major -> blocking; justified-text + all taste = minor -> warning). Verified end-to-end: `node bin/sidecoach-detect.js eval/fixtures/known-defect/gradient-text.html` -> verdict `blocked`, exit 1, gradient-text fires in both static-ban + static-check (unchanged); `.../known-good/clean-page.html` -> verdict `clean`, exit 0, all 4 lenses ran 0 findings (unchanged).

**Verify results:** `--list-rules` prints 60 rules + 9 bindings, exit 0. `npm run build` -> `generate-validators --check: OK (no drift)`. `npm test` -> `76 suite(s) passed` (baseline held; detect-cli + audit-rendered suites green). resolveRenderedRule probe: both ex-orphans resolve, a bogus name returns NULL (gate non-vacuous).
